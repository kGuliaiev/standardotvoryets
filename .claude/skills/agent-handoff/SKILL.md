# Agent Handoff Protocol

## TL;DR — что делать в начале каждой сессии

1. Прочитай эти 5 файлов **до** любого действия:
   - `HANDOFF.md` (корень репо) — снимок состояния
   - `CONTINUATION.md` (корень репо) — живой журнал
   - `CHANGELOG.md` (корень) — что выпущено
   - `docs/DECISIONS.md` — архитектурные решения
   - последние 15 коммитов: `git log --oneline -15`
2. Если эти файлы отсутствуют — твоё ПЕРВОЕ действие создать их (см. §3 и шаблоны ниже), потом начинать работу.
3. Если работаешь >5 минут — после каждой значимой вехи обновляй CONTINUATION.md.
4. Перед паузой/завершением сессии (даже неплановой) — синхронизирующий коммит + push.

## Зачем это нужно

Агенты регулярно сменяются (лимит токенов / падение сессии / Kir переключает агента / iCloud-фриз / ребут). Без живой документации новый агент тратит 30-60 минут на разведку и часто **повторяет уже сделанное** или **ломает ранее принятые решения**. Этот протокол убирает эту цену до ~5 минут на онбординг.

## §1 — Какие документы обязательны

| Файл                       | Назначение                                                                            | Кто обновляет             | Когда                                       |
| -------------------------- | ------------------------------------------------------------------------------------- | ------------------------- | ------------------------------------------- |
| **HANDOFF.md**             | Снимок: как запустить, тесты, стек, prod URL                                          | Любой агент               | При смене стека / структуры / deploy / прав |
| **CONTINUATION.md**        | Живой журнал: текущая ветка, последний коммит, что в работе, открытые задачи, блокеры | Любой агент               | После каждой вехи (фикс, фича, merge)       |
| **CHANGELOG.md**           | Версии релизов                                                                        | Любой агент               | При тегировании версии (vX.Y.Z)             |
| **docs/DECISIONS.md**      | ADR: архитектурные решения, почему так                                                | Любой агент               | При нетривиальном решении                   |
| **QA-tests/YYYY-MM-DD/**   | QA-отчёты по дате прогона                                                             | QA-агенты                 | Каждый QA-цикл                              |
| **TASKS.md** (опционально) | Активный backlog                                                                      | По договорённости проекта | Постоянно                                   |

## §4 — Шаблон docs/DECISIONS.md (ADR)

```
# Architecture Decisions Log

## ADR-001 — Заголовок решения
Дата: YYYY-MM-DD
Статус: Принято / В работе / Отменено
Контекст: какая проблема
Решение: что выбрали
Альтернативы: что отвергли и почему
Последствия: на что влияет в будущем
```

## §5 — Регламент коммитов

1. Conventional commits: `feat(scope): ...`, `fix(scope): ...`, `chore(qa): ...`, `docs(handoff): ...`
2. Каждый фикс / фича / документ-апдейт — отдельный коммит. Не смешивай код и документацию в одном.
3. После любой ветки `feature/*` или `fix/*` → merge в main → push.
4. CONTINUATION.md обновляй отдельным коммитом `docs(continuation): update after <веха>`.

## §6 — Когда обязательно sync-коммит

Не оставляй проект в неконсистентном состоянии. Sync-коммит = `git add -A && git commit -m "wip: state at <дата>" && git push` + обновление CONTINUATION.md.

Обязательно перед:

- Длительной паузой (>30 минут без коммитов).
- Завершением сессии (контекст вышел, ребут, агент устал).
- Передачей контекста другому агенту.
- Любой рискованной операцией (миграция БД, переименование, удаление).

## §7 — Правила онбординга нового агента

Каждый новый агент в первом ответе должен:

1. Подтвердить что прочитал HANDOFF.md, CONTINUATION.md, последние 15 коммитов.
2. Сформулировать одной строкой что он понял про текущее состояние.
3. Назвать ближайшую следующую задачу на основе CONTINUATION.md.
4. Ждать подтверждения от Kir или Dispatch прежде чем начать.

Если HANDOFF.md / CONTINUATION.md устарели — сначала привести их в актуальное состояние, потом работать.

## §8 — QA-цикл

См. `QA-tests/README.md` для деталей. Краткая суть:

- Папка по дате: `QA-tests/YYYY-MM-DD/`
- Файлы: `designer.md`, `backend.md`, `frontend.md`, `summary.md`
- Шаблон отчёта обязателен (severity 🔴🟠🟡ℹ️ + ID + шаги + recommendation file:line).
- Dispatch собирает `summary.md`, передаёт всю папку Code-агенту на `fix/qa-YYYY-MM-DD`.

## §9 — Чего НЕ делать

- Не хранить секреты / пароли / токены в репо (включая HANDOFF/CONTINUATION).
- Не работать на main без коммита — всегда feature-branch или fix-branch.
- Не игнорировать падающие тесты "потом починю".
- Не делать архитектурные изменения без записи в DECISIONS.md.
- Не оставлять PR/ветки без merge или явного DRAFT статуса больше суток.
- Не пушить проект из iCloud-папки (~/Documents, ~/Desktop) — переноси в ~/Private/Claude/.

## §10 — Метрика «как агенту нашли работу»

В конце каждой сессии оставь в CONTINUATION.md строку:
`Session [agent] [start-end time]: closed X tasks, opened Y, next: [task]`
