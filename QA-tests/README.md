# QA-процес — Стандартотворець

Постійний архів QA-прогонів. Кожен значимий реліз або критичний хотфікс
отримує свою датовану папку. Це частина «вічного контексту» проєкту разом
із `CONTINUATION.md`, `HANDOFF.md` і `docs/DECISIONS.md`.

## Структура папок

```
QA-tests/
├── YYYY-MM-DD/                 # дата QA-прогону
│   ├── designer.md             # звіт візуального дизайнера
│   ├── backend.md              # звіт backend-тестера (API/tRPC/RBAC/security)
│   ├── frontend.md             # звіт frontend-тестера (UI/a11y/клієнт)
│   ├── summary.md              # зведення: top issues + handoff для Code-агента
│   └── screenshots/            # скріни (опційно)
└── README.md                   # цей файл
```

## Коли створювати нову папку

- Після кожного значимого релізу (vX.Y.Z).
- Після критичного хотфіксу.
- За прямим запитом Kir.
- Не більше однієї папки на день (якщо кілька прогонів — суфікс `-2`, `-3`).

## Шаблон звіту (обовʼязковий для кожного агента)

Кожен файл (`designer.md` / `backend.md` / `frontend.md`) містить:

### 1. Header

- **Дата:** YYYY-MM-DD HH:MM
- **Версія:** vX.Y.Z (commit hash)
- **Тестер:** Designer / Backend / Frontend
- **Окружение:** local / staging / prod
- **Час перевірки:** XX хвилин

### 2. Що перевірено

Список перевірених областей зі статусом ✅ / ❌ / ⚠️ (не дійшло).

### 3. Статус кожної перевірки

Таблиця: перевірка | статус | час | нотатка.

### 4. Знайдені баги

Кожен баг окремою секцією:

- **ID:** `D-1` / `B-1` / `F-1` (Designer / Backend / Frontend + номер)
- **Severity:** 🔴 critical / 🟠 major / 🟡 minor / ℹ️ info
- **Категорія:** UX / візуал / accessibility / performance / security / data
- **Опис:** що не так
- **Кроки відтворення:** 1, 2, 3
- **Очікувано:** X
- **Фактично:** Y
- **Рекомендація для розробника:** конкретно де правити (`файл:рядок`), що змінити
- **Скріншот (опційно):** `screenshots/D-1.png`

### 5. Рекомендації загального характеру

Не баги, а покращення / observations / tech debt.

### 6. Покриття

Що НЕ покрито перевіркою і чому (out of scope / блокери / nice-to-have).

### 7. Top issues для негайного фіксу

Список ID багів, що термінові (critical + critical major).

## summary.md

Зведений файл з усіма top issues across designer/backend/frontend,
пріоритизація для розробника, handoff message.

## Severity-класифікація

- 🔴 **Critical** — блокує реліз / демо: порожні екрани, втрата даних, security, неробочий core flow.
- 🟠 **Major / High** — серйозно псує UX / стабільність: WCAG fail, race-conditions, неробочі фічі, погано читабельний текст.
- 🟡 **Minor / Medium** — дрібні косяки: spacing/colors не за токенами, незручності, помилки.
- ℹ️ **Info** — observation, не баг.

## Workflow

1. Dispatch запускає 3 QA-агентів паралельно з готовою структурою папки `QA-tests/YYYY-MM-DD/`.
2. Кожен агент пише свій файл за шаблоном.
3. Dispatch (координатор) збирає `summary.md` з top issues + handoff.
4. Передає всю папку Code-агенту: «виправ critical і major, minor за можливості, нічого не ігноруй без обґрунтування».
5. Code-агент створює гілку `fix/qa-YYYY-MM-DD` (або вужчі `fix/<scope>-YYYY-MM-DD`), по кожному ID робить окремий осмислений коміт, тестить, push, merge.
6. Після фіксів — оновлення `CONTINUATION.md` + (за потреби) новий QA-цикл у новій папці.
