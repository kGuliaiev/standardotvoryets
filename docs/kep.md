# ТЗ: КЕП — вход в систему и подписание документов

> Ветка: `feature/kep`. Цель — не трогать `main`, чтобы можно было безболезненно откатиться.
> Статус: согласование ТЗ до начала разработки.

## 0. Краткая суть

Две связанные возможности на базе квалифицированного электронного подписи (КЕП):

1. **Вход по КЕП** — альтернатива логину/паролю; ключ привязан к пользователю.
2. **Подписание документов** — документ можно отправить на подпись участникам РГ; каждый
   накладывает свою подпись через интерфейс `Стандарт → Документ → Підписати`.

Общий фундамент для обеих: подпись формируется на клиенте (плагин КЕП), а **проверяется на
сервере** через публичный сервис проверки ІІТ/ЦЗО, который возвращает данные подписанта
(РНОКПП и т.д.).

## 1. Ключевые решения (зафиксированы)

| Вопрос                       | Решение                                                                    |
| ---------------------------- | -------------------------------------------------------------------------- |
| Канал подписи (сейчас)       | **ІІТ EU Sign (euscp)** — аппаратный токен (флешка) в браузере             |
| Канал подписи (фаза 2, опц.) | **Дія.Підпис** — тот же человек = тот же РНОКПП, привязка переиспользуется |
| Проверка подписи             | **На сервере**, через **публичный сервис проверки ІІТ/ЦЗО** (REST)         |
| Идентификатор личности       | **РНОКПП** (хранится как HMAC-хеш) **+ ID ключа** (серийный № сертификата) |
| Если РНОКПП нет              | матчим по **ID ключа** (для тех, у кого нет РНОКПП)                        |
| Создание аккаунтов по КЕП    | **Нет** — КЕП только привязывается к существующему пользователю            |

**Открытый пункт:** точный REST-endpoint публичного сервиса проверки ІІТ/ЦЗО подтверждаем
на этапе 1 (база — публичный сервис проверки ЦЗО). Если публичного REST не окажется —
fallback: серверная библиотека ІІТ.

## 2. Идентификация подписанта

- Из проверенной подписи сервис возвращает: РНОКПП (для физлиц), ПІБ, серийный № сертификата,
  издателя (ЦСК), срок действия.
- В `User` храним:
  - `kepRnokppHash String? @unique` — HMAC-SHA256(РНОКПП, серверный pepper). Основной идентификатор.
  - `kepKeyId String? @unique` — серийный № сертификата (fallback, если РНОКПП отсутствует).
  - `kepBoundAt DateTime?` — когда привязан (для профиля).
- Открытый РНОКПП **не хранится и не логируется**. Поля КЕП не отдаются клиенту в session.
- Привязка 1:1 (один ключ/один человек → один аккаунт). Уникальность на уровне БД.

## 3. Общий модуль проверки

`src/server/kep.ts`:

- `verifySignature(container, expectedData)` → `{ valid, rnokpp?, keyId, fullName, certInfo }` —
  обёртка над публичным сервисом ІІТ/ЦЗО. Проверяет: валидность подписи, цепочку/срок сертификата,
  и что подписаны именно ожидаемые данные (`expectedData`).
- `identityKeys({ rnokpp, keyId })` → `{ rnokppHash?, keyId }` — нормализация в хранимые ключи.
- Анти-replay: для входа `expectedData` = серверный одноразовый nonce.

# Часть A. Вход по КЕП

## A1. Очевидный результат

- На `/login` есть кнопка **«Увійти за КЕП»**. Вставил токен → подписал → вошёл как свой пользователь.
- В профиле блок **«Електронний підпис (КЕП)»**: состояние (привязан/нет), маскированный
  идентификатор, дата, кнопки «Прив'язати» / «Відв'язати».
- Вход по непривязанному КЕП — отказ с понятным сообщением, **аккаунт не создаётся**.

## A2. Модель данных

- Поля в `User` из §2.
- Одноразовый challenge: `KepChallenge { id, nonce, purpose('login'|'bind'), userId?, expiresAt, usedAt }`
  (TTL ~5 мин, одноразовый). Альтернатива — подписанный JWT-nonce без таблицы (решим на дизайне).

## A3. Потоки

**Привязка (только залогиненный):**

1. Профиль → «Прив'язати КЕП» → сервер выдаёт `nonce` (purpose=`bind`, userId=текущий).
2. euscp читает сертификат, подписывает `nonce`.
3. Сервер: `verifySignature` → получает РНОКПП/keyId → считает ключи.
4. Если уже привязано к другому юзеру → «Цей КЕП вже прив'язано до іншого облікового запису».
5. Иначе сохраняем `kepRnokppHash` + `kepKeyId` + `kepBoundAt` текущему юзеру → запись в ActivityLog.

**Вход:**

1. `/login` → «Увійти за КЕП» → сервер выдаёт `nonce` (purpose=`login`).
2. euscp подписывает `nonce` → контейнер на сервер (через `CredentialsProvider("kep")` NextAuth).
3. Сервер: `verifySignature`, проверяет совпадение с `nonce` и что он не использован/не истёк.
4. Ищем пользователя: сперва по `kepRnokppHash`; если РНОКПП нет — по `kepKeyId`.
5. Нашли и активен → сессия (JWT, как сейчас). Не нашли → «КЕП не прив'язано до жодного користувача».
   Деактивирован → отказ.

**Управление:** «Відв'язати КЕП» из профиля (чистит поля + журнал); админ видит факт привязки
(без РНОКПП) и может отвязать.

## A4. Серверные точки

- `POST /api/auth/kep/challenge` → `{ nonce }` (для `bind` требует сессию).
- `POST /api/profile/kep/bind` / `POST /api/profile/kep/unbind` (требуют сессию).
- NextAuth `CredentialsProvider("kep")` → `authorize({ nonce, container })`.

# Часть B. Подписание документов

## B1. Очевидный результат

- При загрузке/редактировании документа есть галочка **«Потребує підпису»**. Как только она
  поставлена — документ **сразу блокируется от редактирования** и помечается бейджем **«На підписанні»**.
- Требуемые подписанты — **все участники РГ, кроме секретаря**.
- Каждый подписант идёт `Стандарт → Документи → <документ> → Підписати`, вставляет токен,
  подписывает — и его подпись фиксируется.
- У тех, кто ещё **не подписал**, рядом с документом **мигает «ключик»** (call-to-action).
- На карточке документа виден прогресс: **«Підписали 3/8»**, список (хто підписав / коли / хто очікується).
- Подписи проверены сервером и привязаны к конкретным пользователям (по РНОКПП/keyId).

## B2. Модель данных

- `Document`: `signingRequired Boolean @default(false)`, `signingRequestedAt DateTime?`,
  `signingRequestedById String?`. **Пока `signingRequired = true` → документ заблокирован**
  на редактирование/удаление и замену файла (с момента установки галочки, не после первой подписи).
- `DocumentSigner { id, documentId, userId, status('PENDING'|'SIGNED'), required Boolean }` —
  снимок требуемых подписантов на момент запроса (устойчив к изменению состава РГ).
  По умолчанию = **все участники РГ, кроме секретаря (роль `SECRETARY`)**.
- `DocumentSignature { id, documentId, userId, signedAt, signerRnokppHash?, signerKeyId, valid Boolean, storageKey }` —
  факт и контейнер подписи (контейнер кладём в S3, как и документы).
- Тип подписи: **раздельные (detached) подписи** по содержимому документа — по одной на подписанта
  (проще моделировать и проверять, чем мультиподпись в одном контейнере).
- Право `document:requestSign` — новое действие в **матрице прав** (`/admin/permissions`,
  блок «Документи») для **всех ролей**; кто фактически может ставить галочку, решается там.

## B3. Потоки

**Запрос подписей:** пользователь с правом `document:requestSign` ставит галочку «Потребує підпису»
в форме загрузки/редактирования документа → документ **сразу блокируется** → создаются
`DocumentSigner` (все участники РГ, **кроме секретаря**) со статусом PENDING → им уходит уведомление
(новый тип `DOCUMENT_SIGN_REQUEST`) и у них начинает мигать «ключик» на документе.

**Подписание:**

1. `Стандарт → Документи → документ → Підписати`.
2. euscp подписывает **содержимое документа** (его байты/хеш) → detached-контейнер на сервер.
3. Сервер `verifySignature(container, документ)`: проверяет подпись по содержимому, достаёт РНОКПП/keyId.
4. Сверяет, что подписант — это текущий пользователь (его привязанный КЕП) и он есть в списке `DocumentSigner`.
5. Сохраняет `DocumentSignature` (контейнер в S3), статус подписанта → SIGNED → журнал + обновление прогресса.

**Просмотр/выгрузка:** на карточке — список подписей, возможность скачать контейнер(ы) подписи.

## B4. Связь с входом по КЕП

- Подписант должен иметь **привязанный КЕП** (тот же идентификатор). Если подписывает ключом,
  не привязанным к его аккаунту → отказ «Цей КЕП не належить вашому обліковому запису».
- Это переиспользует §2–§3 (идентификация + общий модуль проверки).

## B5. Серверные точки

- `POST /api/standards/[id]/documents/[docId]/sign/challenge` → `{ nonce }` (или подписываем сам хеш документа).
- `POST /api/standards/[id]/documents/[docId]/sign` → принимает контейнер, проверяет, сохраняет.
- tRPC: `document.requestSignatures`, `document.signingStatus`, `document.mySignError` и т.п.

## 4. Безопасность (для обеих частей)

- Подпись проверяется **только на сервере**; «успех в браузере» — не доказательство.
- Вход: одноразовый серверный `nonce` + TTL + анти-replay (повтор контейнера не логинит).
- Подписание: проверяем подпись **по содержимому документа** (а не по произвольным данным).
- Привязка КЕП — **только из активной сессии**.
- Идентификаторы уникальны; РНОКПП — только в виде хеша, не в логах.
- Rate-limit на challenge/verify; все привязки/входы/подписи — в ActivityLog.
- Валидность сертификата (срок/цепочка) проверяет сервис ІІТ/ЦЗО.

## 5. UI

- `/login`: разделитель «або» + «Увійти за КЕП», статусы «Зчитування ключа…», понятные ошибки.
- Профиль: блок «Електронний підпис (КЕП)».
- Документ стандарта: галочка «Потребує підпису» (в форме), бейдж «На підписанні» + «Підписали N/M»,
  мигающий «ключик» у тех, кто ещё не подписал, кнопка «Підписати», список подписантов.

## 6. Конфиг / зависимости

- Клиент: библиотека **euscp** ІІТ + установленный веб-плагин (есть у пользователя).
- Сервер: `KEP_VERIFY_URL` (публичный сервис ІІТ/ЦЗО), `KEP_RNOKPP_PEPPER` (секрет HMAC),
  при необходимости креды сервиса. S3 (уже есть) — для хранения контейнеров подписей.

## 7. Acceptance-критерии (definition of done)

**Вход:**

- [ ] Залогиненный пользователь привязывает КЕП; повторная привязка того же ключа к другому аккаунту — отклоняется.
- [ ] Вход по КЕП пускает именно привязанного пользователя; по неизвестному КЕП — отказ, аккаунт не создаётся.
- [ ] Если РНОКПП нет — вход/привязка работают по ID ключа.
- [ ] Подпись реально проверяется на сервере; поддельный «успех» с клиента не проходит.
- [ ] `nonce` одноразовый; повтор контейнера не логинит.
- [ ] РНОКПП нигде не хранится открыто и не пишется в логи.
- [ ] Логин/пароль продолжает работать как раньше.

**Подписание:**

- [ ] Документ можно отправить на подпись всем участникам РГ (или выбранным).
- [ ] Каждый подписант подписывает через `Стандарт → Документ → Підписати`; подпись проверена по содержимому.
- [ ] Чужим/непривязанным ключом подписать нельзя.
- [ ] Прогресс «Підписали N/M» и список подписантов корректны; подписи можно скачать.
- [ ] Все действия — в ActivityLog.

## 8. Вне обсяга (сейчас)

- Дія.Підпис как канал (фаза 2; переиспользует привязку по РНОКПП).
- Мультиподпись в одном контейнере (используем detached по одному на подписанта).
- Несколько ключей на пользователя (пока 1:1).

## 9. Этапы реализации

1. **Фундамент:** схема БД (поля КЕП + challenge), `server/kep.ts` (проверка через публичный сервис),
   подтверждение REST-endpoint.
2. **Вход по КЕП:** привязка/отвязка в профиле → вход на `/login` (NextAuth provider) → журнал/ошибки/rate-limit.
3. **Подписание документов:** модель `DocumentSigner`/`DocumentSignature` → запрос подписей →
   подписание из карточки документа → прогресс/выгрузка → уведомления + журнал.

## 10. Решённые вопросы

1. **Способ серверной проверки** — _исследовано_: чистого публичного REST-сервиса проверки
   ІІТ/ЦЗО нет (`czo.gov.ua/verify` — портал для людей, не API). Два рабочих варианта:
   - **А.** Серверный компонент ІІТ (HTTP-сервис подписи) → полноценная проверка (подпись +
     статус сертификата через ЦЗО). Надёжнее, но нужно развернуть компонент на сервере.
   - **Б.** Проверка в браузере (euscp) + «полный» контейнер (сертификат+OCSP+TSP вшиты), сервер
     структурно проверяет контейнер и доверяет вшитому OCSP. Без серверного компонента, чуть слабее.
     `server/kep.ts` уже изолирует это за `verifySignature()` — подключим выбранный путь.
2. **Право запрашивать подписи** — новое действие `document:requestSign` в матрице прав для всех
   ролей; конкретное распределение настраивается в `/admin/permissions`.
3. **Блокировка документа** — блокируется **сразу при установке галочки «Потребує підпису»**
   (не после первой подписи). Новая версия = новый документ.
