# Розгортання в закритій мережі (on-prem)

> Документ для ІТ-служби замовника: що потрібно від середовища, яке залізо
> замовляти і як розгорнути систему «Стандартотворець» у локальній мережі без
> доступу до інтернету — щоб можна було вносити документи з грифом ДСК.
>
> Складено з коду репозиторію (`Dockerfile`, `docker-compose.yml`, `.env.example`,
> `src/`) станом на 2026-11-23. Поточне розміщення — Railway,
> `https://standart.202ok.online/`.

---

## 1. Що саме розгортається

Система — це **п'ять процесів**, усі в контейнерах, усі на одному хості:

| Компонент | Образ | Для чого | Обов'язковий |
|---|---|---|---|
| Застосунок | збирається з `Dockerfile` (Node 20) | веб-інтерфейс + API + планувальник | так |
| PostgreSQL | `postgres:16-alpine` | уся структурована інформація | так |
| MinIO | `minio/minio` | файли документів (S3-сумісне сховище) | так |
| Redis | `redis:7-alpine` | черги фонових задач | так |
| Зворотний проксі | `nginx` або наявний у замовника | TLS, єдина точка входу | так |

Планувальник (нагадування, тижневий звіт, нічна вивантажка бази) працює
**всередині застосунку** — окремий сервіс не потрібен.

Поштовий сервер у склад не входить: система надсилає листи через **SMTP
замовника**. Без SMTP система працює, але листи-запрошення й нагадування не йдуть.

## 2. Вимоги до середовища

### 2.1 Операційна система й ПЗ

| | Вимога |
|---|---|
| ОС | Ubuntu Server 22.04/24.04 LTS або RHEL/AlmaLinux 9 — x86-64 |
| Docker Engine | 24+ з плагіном `docker compose` v2 |
| Файлова система | окремий том під дані (`/var/lib/docker/volumes` або винесений) |
| Час | NTP-синхронізація обов'язкова (журнал аудиту, терміни етапів, TOTP у перспективі) |
| Часовий пояс | `Europe/Kyiv` на хості й у контейнерах |
| Локаль | UTF-8 (`uk_UA.UTF-8` або `C.UTF-8`) — уся система кирилична |

ARM (aarch64) теж підійде, але образи треба збирати під цю архітектуру —
готових збірок під ARM ми не тримаємо.

### 2.2 Мережа

| | Вимога |
|---|---|
| Вхід користувачів | HTTPS, 443 — через проксі на порт 3000 застосунку |
| Доменне ім'я | внутрішнє, напр. `standart.local` — потрібне для входу (NextAuth прив'язаний до `NEXTAUTH_URL`) |
| Сертифікат | від внутрішнього ЦСК замовника; Let's Encrypt у закритій мережі не працює |
| Доступ назовні | **не потрібен** після встановлення — див. розділ 4 про те, що для цього треба виправити |
| Доступ до SMTP | до поштового сервера замовника (25/465/587) |
| Внутрішні порти | 5432, 6379, 9000 — **не публікувати** за межі хоста |

> ⚠️ У `docker-compose.yml` зараз порти 5432, 6379, 9000, 9001 прокинуті на хост
> (`ports:`) — це зручно для розробки й неприйнятно на бойовому хості. Для
> встановлення їх треба прибрати, лишивши тільки 3000 за проксі.

### 2.3 Доступ до хоста

SSH з обмеженого кола адрес, вхід за ключем. Обліковий запис із правом
`docker` фактично рівносильний `root` — коло осіб має бути відповідним.

## 3. Чи підійде залізо, яке вже є

Залізо в замовника вже є, тож питання не «що купити», а «чи вистачить». Нижче —
пороги й одна команда, вивід якої дає відповідь.

### 3.1 Пороги

| Параметр | Не запуститься нормально | Працюватиме | Із запасом на 3–5 років |
|---|---|---|---|
| vCPU | < 2 | 2–4 | 8 |
| RAM | < 4 ГБ | 8 ГБ | 16 ГБ |
| Вільний диск під дані | < 40 ГБ | 100 ГБ | 500 ГБ, з розширенням |
| Диск | HDD | SSD | NVMe |
| Архітектура | — | x86-64 | x86-64 |

Пояснення до порогів:

- **RAM 4 ГБ — межа.** PostgreSQL, застосунок, MinIO і Redis разом забирають
  близько 4–5 ГБ під навантаженням. На 4 ГБ система підніметься, але перший
  же експорт великого документа впреться в OOM. 8 ГБ — робочий мінімум.
- **2 vCPU вистачить** для десятків користувачів. Процесор тут не вузьке
  місце — генерація PDF і конвертація `.docx` короткочасні.
- **HDD — єдиний справжній блокер із цього переліку.** PostgreSQL на
  механічному диску дасть помітні затримки на кожній дії, і це не лікується
  налаштуванням. Якщо весь масив на HDD — потрібен бодай один SSD під том
  з базою.
- **ARM (aarch64) не виключений**, але образи доведеться збирати окремо під
  цю архітектуру; готових збірок ми не тримаємо. Скажіть заздалегідь.

### 3.2 Що надіслати, щоб ми дали відповідь

Виконати на машині-кандидаті й надіслати вивід:

```bash
echo "— архітектура та ядра —";  uname -m; nproc
echo "— памʼять —";              free -h
echo "— диски —";                lsblk -o NAME,SIZE,ROTA,MOUNTPOINT; df -h
echo "— ОС —";                   cat /etc/os-release | head -3
echo "— docker —";               docker --version; docker compose version
echo "— чи вільна машина —";     docker ps --format '{{.Names}}'; ss -ltnp | head -20
```

`ROTA=1` у `lsblk` означає механічний диск, `ROTA=0` — SSD.

Окремо, словами, потрібно знати:

1. **Машина вільна чи на ній уже щось працює?** Якщо щось працює — що саме й
   які порти зайняті. Система хоче 3000 (за проксі), 5432, 6379, 9000
   усередині хоста.
2. **Це фізичний сервер чи віртуальна машина?** Якщо ВМ — чи можна
   додати RAM і диск пізніше без перестворення.
3. **Хто адмініструє хост** і чи є на ньому Docker (або чи дозволено
   поставити).
4. **Чи є внутрішній поштовий сервер** і його адреса — без нього не підуть
   запрошення й нагадування.
5. **Чи є внутрішній ЦСК** для сертифіката на внутрішнє доменне ім'я.
6. **Куди складати резервні копії** — потрібен том або хост **поза** цією
   машиною.

### 3.3 Якщо заліза вистачає впритул

Система переживає скромну конфігурацію, якщо прийняти два обмеження:

- **Відмовитись від MinIO** і зберігати файли на диску хоста — мінус
  контейнер і близько 1 ГБ RAM. Потребує правки коду (зараз сховище тільки
  S3-сумісне), тож це окрема робота, а не налаштування.
- **Винести PostgreSQL на окрему машину**, якщо така є. Це найважчий
  компонент, і він єдиний, кого варто відділяти першим.

Обидва варіанти — за потреби; за замовчуванням усе на одному хості.

## 4. Що треба виправити в коді ПЕРЕД закритою мережею

Система писалась під хмару й у кількох місцях ходить в інтернет під час
роботи. У закритій мережі ці місця мовчки відмовлять. Перелік повний,
перевірений по коду.

| № | Що | Де в коді | Що буде в закритій мережі | Складність |
|---|---|---|---|---|
| 1 | Шрифти PDF качаються з `cdn.jsdelivr.net` | `api/meetings/[id]/protocol/route.ts:33`, `api/reports/plan.pdf/route.ts:36` | **PDF протоколу й PDF звіту не формуються взагалі** | пів дня |
| 2 | `seed` виконується на кожному старті | `Dockerfile` CMD | **щоразу відновлює `admin@test.ua` / `Admin123!`** і тестових користувачів | година |
| 3 | `db push --accept-data-loss` на кожному старті | `Dockerfile` CMD | ризик втрати даних при оновленні | пів дня |
| 4 | Шрифт Inter з `fonts.googleapis.com` | `globals.css:5`, `layout.tsx:38-39` | інтерфейс падає на системний шрифт — працює, але виглядає інакше | 2 години |
| 5 | ШІ-чернетка протоколу | `server/ai/protocol.ts` → `api.anthropic.com` | кнопка не працює | вимкнути |
| 6 | Пошта через Resend | `server/email.ts` | листи не йдуть | налаштування |

### Пункт 1 — єдиний, що робить систему неповноцінною

`Font.register()` отримує **URL**, і `@react-pdf/renderer` качає `.ttf` у
момент формування документа. Без інтернету виклик падає, і протокол
засідання в PDF не збирається. Для системи, де протокол — основний вихідний
документ, це блокер, а не косметика.

Лікується просто: покласти три файли Tinos (`Regular`, `Bold`, `Italic`) у
`public/fonts/` і замінити URL на локальний шлях. Шрифт вільний (Apache 2.0),
обмежень на розповсюдження немає.

### Пункт 2 — питання безпеки, а не зручності

Зараз у `Dockerfile` команда старту така:

```
pre-db-push.sh && prisma db push --accept-data-loss && prisma:seed || ... ; pnpm start
```

`prisma:seed` виконується **безумовно при кожному запуску контейнера** і
створює наново обліковий запис `admin@test.ua` з паролем `Admin123!` та
тестових користувачів із `User123!`. У контурі, де лежать документи ДСК, це
неприпустимо: адміністратор видалить тестові акаунти, а наступний
перезапуск їх поверне.

Потрібен прапорець (`SEED_ON_BOOT`), який за замовчуванням вимкнений, і
окремий одноразовий запуск засівання при першому встановленні.

### Пункти 3–6

- **`db push --accept-data-loss`** — компроміс хмарного розгортання
  (ADR-0004). У закритому контурі без можливості швидко відкотитись його
  варто прибрати з автозапуску: схема оновлюється окремою командою під
  наглядом адміністратора, з резервною копією перед тим.
- **Шрифт Inter** — замінюється самохостом через `next/font/local`.
- **ШІ-чернетка** — просто не задавати `ANTHROPIC_API_KEY`; код це вже
  передбачає (`isAiConfigured()`). Треба лише перевірити, що кнопка
  ховається, а не падає з помилкою.
- **Пошта** — задати `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`
  внутрішнього сервера й лишити `RESEND_API_KEY` порожнім. Код уже вміє.

> **Разом на доопрацювання: 2–3 робочих дні.** Після цього система не
> потребує інтернету взагалі.

## 5. Як розгорнути — найпростіший шлях

Найпростіше — **один хост, `docker compose`, усе в контейнерах**. Такий
режим у репозиторії вже передбачений (`--profile fullstack`), його не треба
вигадувати.

### Крок 1. Зібрати образ ЗОВНІ закритого контуру

Збірка потребує інтернету (`pnpm install`, `apt-get`), тому вона робиться на
машині з доступом, а всередину передається готовий образ.

```bash
# на машині з інтернетом
git clone <репозиторій> && cd standardotvoryets
docker build -t standardotvorets:1.0 .

# витягнути ще й службові образи
docker pull postgres:16-alpine
docker pull redis:7-alpine
docker pull minio/minio
docker pull nginx:alpine

# скласти все в один файл
docker save standardotvorets:1.0 postgres:16-alpine redis:7-alpine \
            minio/minio nginx:alpine | gzip > standart-1.0.tar.gz
```

Вийде приблизно 1.5–2.5 ГБ. Переноситься носієм за процедурою замовника.

### Крок 2. Завантажити образи на цільовому хості

```bash
gunzip -c standart-1.0.tar.gz | docker load
```

### Крок 3. Підготувати `.env`

```bash
cp .env.example .env
```

Заповнити (решту лишити як є):

| Змінна | Значення |
|---|---|
| `NEXTAUTH_SECRET` | `openssl rand -base64 32` — **унікальний, не з прикладу** |
| `NEXTAUTH_URL` | `https://standart.<внутрішній-домен>` |
| `NEXT_PUBLIC_APP_URL` | те саме |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` | **змінити** з `minioadmin` |
| `SMTP_HOST` / `SMTP_PORT` | поштовий сервер замовника |
| `EMAIL_FROM` | адреса відправника |
| `RESEND_API_KEY` | лишити **порожнім** |
| `ANTHROPIC_API_KEY` | не задавати |
| `CRON_SECRET` | `openssl rand -hex 32` |

Паролі PostgreSQL і MinIO в `docker-compose.yml` зараз вписані відкрито
(`st_pass`, `minioadmin`) — при встановленні їх треба винести в `.env` і
замінити.

### Крок 4. Запустити

```bash
docker compose --profile fullstack up -d
docker compose ps          # усі healthy?
curl -s localhost:3000/api/health
```

### Крок 5. Створити першого адміністратора

Після доопрацювання за пунктом 2 розділу 4 — одноразовою командою, а не
автоматичним засіванням. До доопрацювання: зайти як `admin@test.ua`,
**негайно змінити пароль**, створити справжніх адміністраторів, тестові
облікові записи деактивувати.

### Крок 6. Поставити проксі з TLS

`nginx` перед застосунком: 443 → `app:3000`, сертифікат внутрішнього ЦСК.
З `docker-compose.yml` прибрати публікацію портів 5432, 6379, 9000, 9001 —
назовні має дивитись тільки проксі.

## 6. Резервне копіювання

У системі вже є нічна вивантажка бази о 03:00 у MinIO зі зберіганням 30 діб.
Цього **недостатньо**: копія лежить на тому самому хості, що й сама база, і
зникне разом із ним.

Потрібно додати:

- щоденне перенесення дампа **за межі хоста** (мережевий том, стрічка,
  інший сервер — за процедурою замовника);
- копіювання вмісту MinIO (самі файли документів), а не лише бази;
- **перевірене відновлення**: бодай один раз розгорнути копію на запасній
  машині й переконатись, що система піднімається. Копія, з якої жодного разу
  не відновлювались, — це припущення, а не копія.

## 7. Спостереження за станом

Зовнішній моніторинг, яким ми користуємось для хмарних сервісів, у закритому
контурі недоступний — він в інтернеті. Всередині потрібне своє:

- `GET /api/health` — зараз відповідає лише «процес живий», **не перевіряючи
  базу й сховище**. Для закритого контуру це варто доробити так, щоб ендпоінт
  читав базу й MinIO і віддавав 503 з причиною, коли щось із них лежить.
  Інакше монітор буде зеленим при непрацюючій системі.
- `GET /api/db-status` — уже перевіряє доступність бази.
- Будь-який наявний у замовника моніторинг (Zabbix, Prometheus, Nagios)
  опитує ці два адреси.

## 8. Що лишається на рішення замовника

Це поза нашою компетенцією — рішення приймає служба захисту інформації:

- потреба в атестації КСЗІ для контуру, де оброблятимуться ДСК;
- шифрування носіїв (LUKS або апаратне) — система цього не робить;
- порядок доступу до хоста й розмежування повноважень адміністраторів;
- строк зберігання журналу аудиту (система веде його без обмеження терміну);
- порядок знищення копій.

Із боку системи для цього вже є: журнал усіх значимих дій
(`ActivityLog` — хто, що, коли, до і після), розмежування прав
(3 глобальні ролі × 5 ролей у групі × ~35 дій із можливістю перевизначення),
вхід за логіном і паролем із блокуванням деактивованих облікових записів.
Чого немає: двофакторної автентифікації, інтеграції з Active Directory,
шифрування даних на рівні застосунку.
